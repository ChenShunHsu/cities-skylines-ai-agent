# Cities: Skylines 1 Autonomous Mayor

Operate the live city through typed tools backed by `http://127.0.0.1:32123`.
Keep safety and verification deterministic while choosing development goals
dynamically from live evidence.

## Apply the Foundation-Model Evidence Lens

Use the detailed
[foundation-model game-AI guide](docs/research/foundation-model-game-ai/README.md)
for autonomy, architecture, memory, and evaluation decisions.

- Treat a live mayor wake as `Play and Act` by default. Do not split the paper's
  six analytical roles into extra agents.
- State the smallest target claim before mutation. Separate live facts supplied
  by CS1/Bridge from goals, candidates, rankings, and hypotheses generated by
  the model.
- Artifact reuse is not capability transfer. Revalidate memory, coordinates,
  entity IDs, route hints, previews, and plans against the current
  `instanceId`, topology, progression, finances, and tool contract.
- Use the guide's E0-E5 evidence ladder. A successful command is E1, not proof
  of a beneficial city outcome. Local settled checks, regression, repeated
  comparable wakes, and multi-save evaluation support progressively broader
  claims.
- If evidence required for a decision is missing, keep the result unknown,
  choose wait/defer, or add deterministic telemetry. Never fill the gap with a
  screenshot, model self-evaluation, or an old artifact.

At the end of every material wake, include a compact `Foundation-model lens`
block with the primary role, target claim, supplied facts, generated decisions,
reused artifacts, live revalidation, evidence level and scope, and the next
recheck condition.

## Use a Grounded Planning Pipeline

This section is an operating policy, not a claim that every domain already has
the same planner. The road corridor implements the most complete current
sampler/search path; other domains do not yet share a generic prerequisite
planner or an evidence-envelope ranker.

For every objective, keep prerequisite planning, continuous candidate generation,
environment verification, ranking, and mutation as separate stages:

1. Derive discrete prerequisites from live progression and topology. When a
   prerequisite is absent, make it the next subgoal instead of guessing an
   asset, coordinate, or workaround.
2. Ask the domain sampler for geometry-derived candidates. Candidate streams
   may use live terrain, road tangents, widths, zoning cells, resources, and
   service fields; they must not use a map name, city ID, entity ID, or fixed
   world coordinate as policy.
3. Filter with current unlock, native preview, reserve, topology, access, and
   safety gates. These environment-supplied feasibility checks are
   authoritative and cannot be offset by urgency, impact, confidence, or a
   model preference.
4. Rank only the surviving candidates by evidence freshness and scope, goal
   utility, verified reliability, cost, risk, and repetition penalty.
5. Execute at most the first freshly verified step. Settle, inspect, run the
   regression check, and replan from the new live state before using any later
   conditional step.

Record stream diagnostics as `generated transition attempts → statically
eligible attempts → locally evaluated preview variants → locally accepted
variants` when bounded planning fails, and use the separate global native-call
counter for actual Bridge requests. This distinguishes candidate generation,
engine rejection, acceptance policy, scheduling, execution, and recovery
instead of treating every failure as an unsafe coordinate.

Only an E3 terminal success may be distilled into a reusable workflow. Reuse
parameterized prerequisites and verification steps, never prior coordinates,
entity IDs, or preview results. Invalidate the workflow when its declared
Bridge/tool revision, progression mode, or world scope no longer matches.
No workflow extractor or registry is implemented yet; this is an eligibility
rule, not authorization to persist a reusable workflow.

## Start Each Wake

1. Immediately pause with `set_simulation_speed`. Keep the game paused while
   reading evidence, reasoning, previewing, and selecting actions so planning
   time cannot consume the city budget.
2. Load memory with `load_mayor_memory`. The tool must compare the live
   `instanceId` itself and atomically reset goals, coordinates, entity IDs,
   cooldowns, and snapshot history when the city changes.
3. Call `validate_progression_mode`, then read one compact snapshot with
   `observe_city`. Stop without mutation if normal progression is not verified.
4. Confirm the returned memory scope matches the snapshot. Never copy
   coordinates, node/segment/building IDs, or blockers from an earlier city.
5. Compare progression capabilities with `lastSnapshot`; never use locked zones,
   services, assets, or transport types.
6. Infer the current phase: `bootstrap`, `early-growth`, `service-expansion`,
   `transit-growth`, `optimization`, or `recovery`.
6. Preserve useful active goals. Complete, block, or replace goals only when
   current evidence justifies the change.

Invoke a typed tool from the repository when native function registration is
not available:

```powershell
python .\scripts\mayor_tools.py definitions
'{"detailLimit":10}' | python .\scripts\mayor_tools.py call observe_city --arguments-file -
```

Read [references/mayor-tools.json](references/mayor-tools.json) when registering
function-calling tools. Read
[references/mayor-memory.schema.json](references/mayor-memory.schema.json)
when creating or repairing persistent memory.

## Choose, Do Not Script, the Goal

Generate several candidates from the snapshot, city vision, active goals, new
unlocks, demand, capacity, coverage, traffic, physical zoning capacity, and
recent actions. Always include "wait and simulate" when no mutation is
justified.

Use `score_candidates` with:

- urgency;
- resident or city impact;
- confidence in the evidence;
- alignment with the city vision;
- cost relative to reserve;
- geometry and operational risk;
- repetition penalty or cooldown.

Treat scoring as decision support, not permission. Reject hard-blocked
candidates regardless of score. Choose zero to three independently justified
or safely ordered actions per wake. Do not add filler actions.

## Hard Gates

- Reject anything not currently unlocked.
- Reject the entire mutation cycle when `validate_progression_mode` detects
  Unlock All, Unlimited Money, developer mode, or stale test-save evidence.
- Refresh loaded prefab lists before construction.
- After a road satisfies a create-pass milestone, call
  `inspect_toolbar_unlocks`. Newly reported zoning, electricity, water, or
  service capabilities are not usable until the matching live toolbar button
  is found, enabled, visible, interactive, and consistent with
  `UnlockManager`. Do not use command APIs to bypass a stale locked toolbar.
- Create and verify a named checkpoint before every mutation.
- Simulation pause/speed control is the only operational exception to the
  checkpoint rule. Resume at a safe speed when settlement evidence is needed.
- Call `preview_building_candidate` before every building placement or move.
  Its game-native placement, footprint, road-access, terrain, pollution,
  ground-water, utility, and production hard gates are authoritative.
- Preview service impact and networks before construction.
- Maintain a recent offline spatial snapshot when the game may close or when
  full-city spatial analysis would be too expensive during a wake. Use
  `scripts/capture-offline-spatial-snapshot.ps1` while the Bridge is available.
- While a city is live, offline spatial tools must capture that current city
  when no path is supplied and reject every snapshot whose `instanceId` differs
  from the live city. A matching map name is never sufficient evidence.
- Use `inspect_planning_area` to reduce a captured city to the local 3D,
  terrain, resource, utility, road, building, and demand evidence needed for
  one decision. Use `propose_development_plan` to compare ranked alternatives,
  not to authorize construction. Its anchors are exact captured terrain
  samples, but every road, utility, zoning, or building action still requires
  fresh live unlock, cost, native preview, topology, and pathfinding checks.
- Use `inspect_road_layers_3d` and `inspect_grade_separated_crossings` for road
  planning and verification. A two-dimensional crossing is not an overlap when
  interpolated road heights prove a bridge, elevated road, or tunnel separation.
  Treat `UnconnectedSameGradeCrossing` as a hard anomaly requiring recovery or
  focused live inspection.
- On a fresh map, call `propose_outside_road_connection` before guessing
  individual highway-transition segments. Build only its native-previewed
  ordered plan, with a new checkpoint and regression baseline per segment.
  When the returned plan is `iterative`, build only its single segment, finish
  settled verification, and rerun the planner from live topology.
  Never bypass `nativeMoveMiddleNodeRisk`; it means CS1 would rewrite an
  existing road and local entity rollback would not be reliable.
- Use `inspect_building_layers_3d` and
  `inspect_building_road_clearance_3d` when a building footprint overlaps a
  road in XZ. Accept a tunnel or elevated road only when native building
  vertical bounds and native road curves prove clearance. Never use visual mesh
  bounds as the building foundation.
- Before placing a noisy utility or a geographically distributed service,
  inspect native source parameters with `inspect_facility_influence` and the
  propagated live `NoisePollution`, police, healthcare, fire, or education
  field with `inspect_service_coverage`. A declared radius is not proof of
  effective live coverage.
- Do not invent coordinates by offsetting, averaging, or copying another
  facility. Use exact road, zoning, resource, terrain, and collision evidence.
- Keep cash above the memory's reserve policy.
- Treat CS1 monetary API values as internal hundredths. Use `amountDisplay` and
  `periodNetDisplay` from `observe_city` for planning and reporting; never
  present raw internal values as visible in-game currency.
- Physical growth outranks fiscal tuning when cash is above reserve, utilities
  are healthy, demand is positive, and vacant zoned supply is below the
  `growthPacing` target. Generate a road or zoning candidate before any fiscal
  candidate.
- Never adjust taxes or service budgets in consecutive wakes. The typed tools
  enforce a 60-minute cooldown (four 15-minute wakes), and only one fiscal
  action is allowed in a wake.
- Hard-block a fiscal candidate unless it addresses `TaxesTooHigh`, a deficit
  sustained across at least two snapshots, capacity that is unavailable,
  critical, or at least 90% utilized, or correction of a failed fiscal change.
  State a measurable expected outcome. Do not use financial analysis to crowd
  out affordable physical expansion.
- When period net is negative, reject service-budget increases unless live
  capacity is unavailable, critical, or at least 90% utilized.
- Call `preview_district_specialization` before applying industry
  specialization. Use `requireLocalResource=true` when the goal is local
  extraction; otherwise explicitly account for the reported import dependency.
- Before placing an intake or sewage outlet, call `inspect_water_pair`; require
  moving water, consistent flow, an upstream intake, a downstream outlet, safe
  separation, an unpolluted intake sample, valid shoreline orientation, and
  nonzero native production. If the bounded native candidate search returns no
  valid pair, stop water construction. Never weaken these hydrology gates or
  place facilities from guessed coordinates.
- Before laying any water pipe, call `preview_water_system_plan`. Require one
  intake branch, one outlet branch, at least one shared-trunk segment, a
  three-way shared junction, and a trunk endpoint in the serviced city area.
  Never connect the intake and outlet directly. The generic `build_network`
  mutation intentionally rejects Water prefabs; use `build_water_pipe` with the
  complete verified plan and a fresh checkpoint for each segment. Build in
  `segmentIndex` order; later calls verify preceding segments against the live
  Water network and preview only the unbuilt remainder.
- After the complete pipe plan is built, call
  `inspect_water_network_topology`. Require an intermediate shared-trunk node,
  an off-path serviced-area branch, at least three component segments, and no
  direct facility-to-facility pipe. Then call
  `inspect_water_service_coverage` and verify exact demanding buildings have
  both water and sewage without polluted water.
- Before placing any power plant, call `preview_power_plant_candidate` and use
  `place_power_plant`; the generic `place_service` tool intentionally rejects
  power plants. For wind turbines, require the native location-dependent output
  ratio to meet the plan threshold. For coal or oil plants, require zero
  residential noise and ground-pollution exposure plus directed inbound and
  outbound freight reachability to an outside road connection with bounded
  route distance and congestion. Native `RequireRoadAccess()` is automatic and
  mandatory: require the calculated sidewalk access point to reach a ground
  vehicle lane within 20 metres. After placement, require a nonzero native
  `accessSegmentId`; the mutation must roll back a plant with
  `RoadAccessFailed`.
- After a power plant settles, call `inspect_power_plant_operation`. Require
  positive production, no live building problems, adequate native fuel buffer
  for fuel-based plants, continued two-way freight reachability, and zero
  demanding buildings from `inspect_electricity_service_coverage` that remain
  without electricity. Native
  route telemetry does not expose every modded turn restriction or district
  heavy-traffic rule, so verify that actual fuel vehicles acquire paths before
  treating a fuel plant as reliable.
- Before connecting one generator to multiple facilities or growable
  buildings, call `propose_minimal_power_grid` with every relevant building
  blue electricity region. Do not independently connect every target back to
  the generator. Accept zero-length native-radius overlaps, then build the
  returned native-previewed minimum tree in source-outward order. Build a line
  only when both selected endpoint samples report native `conductive: true`;
  nominal blue-radius membership alone is insufficient. Create a
  separate checkpoint and regression baseline for each segment, let power
  propagation settle, re-read every target's connection area, and rerun the
  planner for the remaining targets before continuing because water levels,
  collisions, and newly conductive growables can invalidate a static later
  edge. After growables bridge previously separate areas, use
  `inspect_power_grid_efficiency` for one-at-a-time removal experiments rather
  than preserving redundant startup lines.
- Zone only blocks returned as `developmentFrontageSafe`. Blocks at a junction
  are zoned as a player zones them: the game invalidates the cells another
  road's blocks overlap (`junctionClearanceSafe` only reports the 64-metre
  nearness). Pass the returned exact `blockId`;
  use center/radius zoning only for compatibility with older callers.
- Require road access and reject building-road or building-building overlap.
- For fuel power plants, use the road-edge candidates and road-facing angles
  returned by `propose_power_plant_candidates`; do not guess placement from a
  coarse terrain sample or add a road only to reach an arbitrary sample.
- Call `preview_transport_plan`; require compatible network within 64 metres of
  every stop, at least 32 metres between stops, and an active bus depot.
- Call `preview_bulldoze_impact` before every deletion. Never remove non-empty
  storage, an assigned depot, a last active service facility, a network cut
  edge, or an outside connection without explicit risk confirmation and a
  verified recovery plan.
- Call `preview_operational_change` before disabling a building.

## Adaptive Development Heuristics

- Read `assess_city.planningHints`; they compress sourced CS1 knowledge from
  `references/cs1-gameplay-rules.json`. Early deficits are normal, residential
  growth is the main income lever, and oversupplied utility budgets can be
  trimmed. Open `docs/research/cs1-planning-knowledge-zh-TW.md` only to change rules.
- In `bootstrap`, establish valid outside-road access, power, water, sewage,
  small zoning blocks, and a positive or recoverable budget.
- In `early-growth`, keep vacant zoned supply ahead of high demand up to the
  `growthPacing` target and per-wake block cap. Zone in small repeated batches
  rather than one large area, which avoids death-wave age cohorts. Pacing counts
  `developableVacantCells`: a vacant cell behind an occupied or invalid cell in
  the same row can never host a growable, so `strandedVacantCells` is not supply.
- In `service-expansion`, compare citywide capacity with geographic coverage.
  Use `preview_service_impact` and prefer the candidate that helps uncovered
  residents with the least redundant coverage and safe maintenance cost.
- In `transit-growth`, require unlocked modes, reachable stations/stops, route
  continuity, demand evidence, and affordable operating cost.
- In `optimization`, improve traffic, coverage, zoning efficiency, and budgets
  without manufacturing construction work.
- Enter `recovery` after a failed verification or material regression. Roll
  back only the new entity when safe; otherwise restore the checkpoint.

## Mutation Protocol

For each selected action:

Use the steps below as the target orchestration record: `PLANNED → PREVIEWED →
CHECKPOINTED → BASELINE_CAPTURED → INTENT_RECORDED → SENT → RECONCILING →
SETTLED → FOCUSED_VERIFIED → REGRESSION_PASSED → SAVED`. This is not yet one
shared persisted controller. Ground-road builds automate pre-send intent
recording, bounded settled finalization and local rollback; the caller still
coordinates checkpoint, baseline, focused QA, regression and save. If execution
is interrupted or its response is ambiguous, reconcile the live entity and
journal before retrying. Never resend merely because a request timed out.

1. Read the focused evidence required for that domain.
2. Preview the exact candidate.
3. Call `create_checkpoint` and retain its verified name.
4. Call `capture_regression_baseline` with a unique baseline name.
5. Execute one typed mutation with that checkpoint name.
6. Use `set_simulation_speed` when necessary and wait for the simulation to
   settle long enough for the target metric or problem to update.
7. Read back the affected entity, its focused anomalies, and
   `verify_regression` for the baseline.
   For every road build, upgrade, or reversal, also call
   `inspect_road_result` and confirm lane directions, endpoint logic, terrain
   profile, outside connectivity, layered structure type, and grade-separated
   crossings. If deterministic telemetry is missing or ambiguous, stop and add
   the missing telemetry; never fall back to screenshots or image inspection.
   The tool must use the mutation's returned segment ID, the segment's current
   native Bezier, live terrain samples, live endpoint nodes, and directed
   outside reachability. A stored coordinate, map name, road name, or prior
    entity ID is never acceptable verification evidence.
    After a road mutation, drain the game-thread state barrier before final
    inspection so junction, terrain, and native Bezier updates have settled.
    Compare endpoint identity in XZ; verify Y independently through the live
    native curve and terrain profile because CS1 settles road nodes vertically.
   A ground-road preview must keep the complete centerline within 1 metre of
   sampled terrain. Split a rejected long alignment into shorter
   terrain-following segments; never raise this limit to make a buried or
   floating road pass. The non-dry-run road command repeats the checks and
   locally rolls back a newly created segment if its actual native curve fails.
   Absolute deviation alone is insufficient: the calculated visible surface
   of every sampled Ground-road point (native curve plus that live segment's
   measured node-to-curve vertical inset) must remain at or above live terrain
   within the tool's small numerical tolerance. Do not interpret prefab-local
   mesh axes as world height or classify CS1's lower Bezier centerline by
   itself as a buried visible road. Only explicit
   slope/tunnel/underground construction may otherwise be below terrain. Treat
   `roadBelowTerrain` as blocking
   after any later mutation, because junction and renderer refreshes can expose
   a previously hidden intersection with terrain.
8. Accept the change only when the targeted symptom improved and no material
   city regression appeared. Otherwise remove only the new entity when safe or
   restore the checkpoint, then verify recovery.
9. Only after the action passes or recovery is verified may the wake continue
   to another action or finish.

Never call `/commands/restore-checkpoint` to hot-load a save inside a running
CS1 level. A verified live failure displayed `File format version not
supported` while the Bridge incorrectly reported `loaded`, and the economy
state was not restored. When local recovery is insufficient, keep the
simulation paused, stop further mutation, fully restart Cities: Skylines, load
the verified checkpoint through the normal load-game flow, and then re-run the
focused and regression checks.

After successful actions, save and verify the city. Never treat a successful
command response alone as proof that the action is valid. A wake must not go
offline while the result of its latest mutation is untested or ambiguous.
Only after every accepted action passes deterministic API and telemetry checks may the mayor
resume simulation at a safe speed. If any action fails or recovery is
incomplete, keep the game paused.

## Persist the Mayor's Intent

After every wake, use `save_mayor_memory` to update:

- city vision and inferred phase;
- active goals with metrics, priorities, evidence, and recheck conditions;
- verified, failed, rolled-back, and deferred actions;
- blockers and the exact condition that can unblock them;
- cooldowns that prevent repetitive construction or budget changes;
- a compact last-snapshot summary and observed unlock changes.

Keep at most 100 recent actions. Do not store large API responses in memory.
Write all goals, reports, and action rationales in English.

## Finish the Wake

Account for every material recommendation as accepted, combined, deferred, or
rejected. Report the chosen goal, evidence, mutations, verification, budget
effect, unresolved risks, and the next recheck condition. It is valid to make no
change when evidence does not justify one.
