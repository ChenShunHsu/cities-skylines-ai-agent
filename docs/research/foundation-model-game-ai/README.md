# Foundation Model 遊戲 AI：CS1 Autonomous Mayor 使用指南

> 論文：[AI for Games in the Foundation Model Era](https://arxiv.org/abs/2609.16679)
> · [Hugging Face](https://huggingface.co/papers/2609.16679)

本文件把論文轉成 agent 可執行的判斷規則；它不是新增功能、遊戲實測，
也不證明自主市長已能長期經營城市。

---

## 一句話結論

agent 的底層模型是 foundation model，但這個專案中的「自主市長」不是只有模型：
它是 **foundation model + typed tools + live telemetry + deterministic safety gates +
game simulation + persistent memory** 組成的控制迴路。

論文最有用的地方，不是叫專案換模型或增加 agent，而是要求 agent 每次清楚回答：

1. 模型現在扮演哪一種角色？
2. 哪些資訊由遊戲／Bridge 提供，哪些內容由模型產生？
3. 重用的是 artifact，還是真的證明能力能 transfer？
4. 現有證據最多能支持多大的主張？

---

## 1. 六種角色如何對應本專案

論文的六種角色是分析分類，不是要求建立六個 agent，也不是模組清單。

| 論文角色 | 本專案對應 | 適用程度 | agent 應如何使用 |
|---|---|---:|---|
| Play and Act | 觀察城市、選擇目標、呼叫 typed mutation、驗證結果 | 主要角色 | 把每次 wake 視為有界的 observe-plan-act-verify 迴路 |
| Model Players and Games | `observe_city`、assessment、snapshot、memory 對城市狀態的摘要 | 部分適用 | 摘要是決策支援，不可冒充完整模擬器或玩家模型 |
| Design Games | 修改 CS1 規則、關卡、任務或遊戲設計 | 通常不適用 | 規劃城市道路與分區仍是 gameplay，不等於設計 CS1 這款遊戲 |
| Build and Maintain Games | C# Bridge、Python tools、schemas、測試與文件 | 開發期角色 | 寫程式時用軟體工程證據，不可把測試通過當成 live city 成效 |
| Generate and Adapt at Runtime | 依 live 狀態調整目標、候選、記憶與有限內容 | 部分適用 | 每次適應都受 unlock、cash、geometry、preview 和回歸門檻限制 |
| Test and Evaluate Games | native preview、checkpoint、settlement、focused QA、regression | 主要支援角色 | evaluator 必須用可觀測結果判定，不採信模型自己的合理化說明 |

預設判斷：

- 操作 live city：主要是 **Play and Act**。
- 修改 Bridge／工具：主要是 **Build and Maintain Games**。
- 驗證一次操作：主要是 **Test and Evaluate Games**。
- 不要因同一個 agent 同時涵蓋多種角色，就推論它已具備通用遊戲智能。

## 2. Boundary：模型與遊戲各自負責什麼

| 層次 | 必須負責的內容 | 不得越界 |
|---|---|---|
| CS1 simulation | 經濟、交通、需求、pathfinding、解鎖與時間後果 | agent 不可自行假設模擬結果 |
| Bridge / typed tools | live telemetry、entity identity、native preview、hard gates、mutation result | 工具回傳成功不可宣稱城市已改善 |
| agent | 目標、候選方案、排序、理由、未知項目與下一次 recheck | 不得捏造 telemetry、座標、原生檢查或 unlock |
| Deterministic evaluator | settlement 後 focused QA、regression、recovery 判定 | 不以模型自評取代可重現檢查 |
| Persistent memory | 保存已驗證結果、失敗、阻擋與適用範圍 | 不把未驗證假說升級成通用策略 |

agent 可以提出「興建道路可能解除住宅 frontage 瓶頸」；但道路是否合法、
是否真的連通、城市是否在 settlement 後改善，必須由 Bridge 與遊戲證據回答。

若缺少判斷所需 telemetry，正確行為是保持未知、等待，或先補 telemetry；
不是改用截圖、語言推測或舊座標填空。

## 3. Reuse 不等於 Transfer

可重用的 artifact 包括：

- city vision、active goal、成功條件與 recheck condition；
- snapshot 摘要、失敗原因、cooldown、候選生成模式；
- 工具 schema、測試 fixture、preview 與 regression 流程；
- 過去證實「在什麼條件下」有效或無效的策略紀錄。

重用前仍必須以 live city 重新確認：

- `instanceId` 與存檔範圍；
- entity ID、座標、道路拓撲與 native curve；
- prefab、toolbar 與 progression unlock；
- cash、reserve、需求、容量和服務覆蓋；
- terrain、collision、pathfinding、native preview；
- tool schema、Bridge 版本與目前可觀測欄位。

禁止直接 replay 舊城市的座標、entity ID、道路方案或 preview 結果。
一次成功最多證明該 action 在當時條件下通過；它不自動證明能 transfer 到其他
存檔、地圖、城市階段或 Bridge 版本。

## 4. Evidence：主張只能到證據所在層級

| 層級 | 已有證據 | 可以說什麼 | 不可以說什麼 |
|---|---|---|---|
| E0 設計 | 文件、prompt、planning-only 輸出 | 有一個候選設計 | 功能已可用 |
| E1 執行 | API 接受、entity 建立、command success | 命令已執行 | 城市已改善 |
| E2 局部結果 | settlement 後目標 entity 與 focused telemetry 通過 | 這次局部操作符合目標 | 沒有系統性副作用 |
| E3 系統安全 | E2 + regression + save/recovery 驗證 | 這次 wake 未發現受測範圍內的重大回歸 | 能長期自主經營 |
| E4 持續效果 | 多個可比較 wake、預先定義指標與觀察期限 | 在這個城市與階段呈現持續效果 | 可泛化到別的地圖 |
| E5 Transfer | 多存檔／多地圖／多階段，在相同介面與預算下重複驗證 | 在明示測試範圍內具有 transfer 證據 | 通用或無條件能力 |

報告應使用到達的最高證據層級，不得用語氣把 E1 包裝成 E3，
或把單一 live run 包裝成 E5。離線 fixture 可驗證解析、schema 和決策邏輯，
不能證明真實 CS1 settlement 後的城市結果。

## 5. agent 每次 wake 的套用方式

仍以根目錄 [SKILL.md](https://github.com/ChenShunHsu/cities-skylines-ai-agent/blob/main/SKILL.md) 為執行契約；
本文件不放寬任何 hard gate。

1. **Observe**：暫停、核對 `instanceId`、progression、memory scope 與 compact snapshot。
2. **Frame the claim**：寫出本次想證明的最小主張，例如
   「此段道路能安全增加可分區 frontage」，不要先宣稱「城市會繁榮」。
3. **Classify**：標記主要論文角色；live 操作預設是 Play and Act。
4. **Separate the boundary**：列出遊戲／Bridge 已提供的事實，以及 agent 生成的候選與假說。
5. **Generate alternatives**：至少保留 wait/defer；候選不足時不可用猜測補齊。
6. **Revalidate reuse**：任何來自 memory、snapshot、舊 route 或摘要的 artifact，都以 live evidence 重驗。
7. **Execute safely**：exact preview → checkpoint → regression baseline → one typed mutation。
8. **Evaluate**：等待 settlement，讀回 focused telemetry，執行 regression 與必要 recovery。
9. **Bound the conclusion**：依 E0–E5 回報證據範圍、未知項目及 next recheck condition。
10. **Persist carefully**：記錄觀測與失敗；只有通過門檻的結果才能標為已驗證策略。

初期或新類型操作應一次只改一項，使失敗可歸因、可回復。
若現有 [compact mayor 流程](../../guide/compact-mayor.md) 或 domain hard gate
更嚴格，以較嚴格者為準。

## 6. agent 回報模板

每次涉及 mayor autonomy、架構選擇或 live mutation 的報告，至少包含：

```text
Foundation-model lens
- Primary role:
- Target claim:
- Supplied by CS1 / Bridge:
- Generated by agent:
- Reused artifacts:
- Live revalidation:
- Evidence level: E0-E5
- Evidence scope:
- Unknowns / next recheck:
```

簡例：

```text
Foundation-model lens
- Primary role: Play and Act
- Target claim: 新道路可安全增加住宅 frontage
- Supplied by CS1 / Bridge: live topology、terrain、unlock、native preview
- Generated by agent: 候選排序與選擇理由
- Reused artifacts: 上次 wake 的 active goal
- Live revalidation: instanceId、cash、route、preview 已重驗
- Evidence level: E3
- Evidence scope: 單一存檔、單一 settled mutation
- Unknowns / next recheck: 尚無持續入住證據；下一會計／成長週期重查
```

## 7. 對後續架構工作的優先順序

1. 先補能判斷城市結果的 telemetry，再增加 prompt 複雜度。
2. 維持 planner 與 deterministic evaluator 的責任分界。
3. 讓 memory 保存 scope、證據層級、版本與撤銷條件，不只保存結論。
4. 對長期主張使用多 wake 的成功條件與停止條件。
5. 要宣稱 transfer 前，建立多存檔／多地圖、固定預算與介面的評估集。
6. 保留 interruption、recovery、resume 與 human handoff；長期自治不能只測理想路徑。

---

## 8. 這篇論文不授權的事

- 不因 agent 使用 foundation model 就略過 typed tools 或 deterministic gates。
- 不以模型的 chain-of-thought、自評或自然語言合理性當成遊戲結果。
- 不為了符合六種角色而建立多 agent。
- 不把 city layout planning 說成 game design 成果。
- 不把 artifact reuse 說成 capability transfer。
- 不把 command success、單次道路成功或離線測試說成持續自主經營。
- 不改變 zero-image 原則，也不以截圖補足缺失 telemetry。
